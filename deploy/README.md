# Установка жителя машины

Бинарник **кросс-компилируется**, а не собирается на месте: на целевой
машине не нужны ни Go, ни исходники (design.md, решение 4). Порядок один
на все системы — положить бинарник, поставить службу, ввести одноразовый
код, убедиться, что агент виден Сёме; различается только файл службы.

Что лежит рядом:

| Файл | Для чего |
|---|---|
| `semaagent.service` | Linux, служба системы от своего пользователя: VPS, машина сборки — там, где человек не один |
| `semaagent.user.service` | Linux, служба человека (`systemctl --user`): личная рабочая машина, где житель читает репозитории человека |
| `semaagent.plist` | мак, `launchd` (шаблон: пути подставляет `install-mac.sh`) |
| `install-mac.sh` | тот же порядок на маке одной командой |

## От какого пользователя

Роль у агента одна, а вид службы — два, и выбирается он не по вкусу.
Житель машины отвечает хукам Claude Code и Codex, а те запускаются от
человека и ищут местную дверь в его домашнем каталоге
(`~/.sema-agent/agent.sock`, права 0600). Значит:

- **личная машина** (мак, ноутбук, рабочая станция) — служба человека:
  `semaagent.user.service` или `launchd`. Житель видит репозитории и
  сокет;
- **общая машина** (VPS) — служба системы от пользователя `semaagent`:
  удостоверение агента не лежит в домашнем каталоге человека, которого
  тут несколько. Карточки кода в этом виде бесполезны — репозиториев
  агент не видит; годится он для той работы, где файлы человека не нужны.

## Linux: служба человека

```sh
# на своей машине (там, где есть Go)
make linux                      # dist/semaagent-linux-amd64 и -arm64
scp dist/semaagent-linux-amd64 человек@машина:/tmp/semaagent

# на целевой машине
mkdir -p ~/.local/bin ~/.config/systemd/user ~/.sema-agent
chmod 700 ~/.sema-agent          # в нём удостоверение агента
install -m 0755 /tmp/semaagent ~/.local/bin/semaagent

# файл службы: подставить адрес Сёмы
sed 's|@АДРЕС_СЁМЫ@|sema.local:8766|' semaagent.user.service \
    > ~/.config/systemd/user/semaagent.service

# одноразовый код — с экрана «Агенты» у Сёмы; роль человек выбирает там же
~/.local/bin/semaagent -enroll <код> -sema http://sema.local:8765

systemctl --user daemon-reload
systemctl --user enable --now semaagent
# служба должна жить и без входа в систему
loginctl enable-linger "$USER"
```

## Linux: служба системы

```sh
sudo useradd --system --home-dir /var/lib/semaagent --shell /usr/sbin/nologin semaagent
sudo install -m 0755 /tmp/semaagent /usr/local/bin/semaagent
sudo sed 's|@АДРЕС_СЁМЫ@|sema.local:8766|' semaagent.service \
     > /etc/systemd/system/semaagent.service

# каталог состояния делает systemd (StateDirectory, права 0700), но
# удостоверение получает сам агент — от имени своего пользователя
sudo install -d -o semaagent -g semaagent -m 0700 /var/lib/semaagent
sudo -u semaagent /usr/local/bin/semaagent -enroll <код> \
     -sema http://sema.local:8765 -home /var/lib/semaagent

sudo systemctl daemon-reload
sudo systemctl enable --now semaagent
```

## Мак

```sh
./deploy/install-mac.sh sema.local:8766
```

Скрипт собирает бинарник, кладёт в `~/.local/bin`, разворачивает шаблон
plist с настоящими путями и перезагружает службу. `launchctl bootout` перед
`bootstrap`, а не `kickstart`: `kickstart` перезапускает процесс по уже
загруженному описанию и изменений в plist не видит. И **после `bootout`
надо ждать**, пока служба действительно ушла: он возвращается раньше, чем
launchd её убрал, и следующий `bootstrap` падает с «Input/output error»,
после чего нет ни старой службы, ни новой (наступали 27 сентября 2026).

## PATH службы — не мелочь

Служба получает урезанный PATH, а житель машины ищет на диске языковые
серверы, `ctags`, `ripgrep` и `swiftc`. Поэтому PATH задан в файлах службы
явно, и в нём обязан быть `~/go/bin`: там лежит `gopls`, поставленный
`go install`. Без него Go — язык самой Сёмы и этого агента — отвечает
ярусом `ctags` вместо `lsp`, и узнать об этом можно только по капсуле яруса
в ответе: карточки приходят, просто хуже. Проверка — `agent_status`: у
языка должно стоять «готов», а не «нет сервера».

## Проверка после установки

1. Служба поднялась: `systemctl --user status semaagent`
   (`launchctl print gui/$UID/org.example.semaagent` на маке).
2. Провод жив: в журнале строка о подключении к Сёме
   (`journalctl --user -u semaagent -f`, на маке `~/.sema-agent/agent.log`).
3. Агент виден Сёме: экран «Агенты» — имя, отпечаток, **роль** и версия.
   Способности там же приходят выключенными: разрешает их человек поимённо.
4. Права: `ls -ld ~/.sema-agent` — `drwx------`; `ls -l ~/.sema-agent` —
   `cert.pem`, `key.pem`, `role` с правами `0600`; сокет `agent.sock` —
   `srw-------`. Сосед по машине их не читает.
5. Перезагрузить машину — агент поднялся и подключился сам.

## Обновление на месте

Замена бинарника и перезапуск службы. Удостоверение, роль и разрешённые
способности лежат в каталоге состояния и замену переживают — заводить
агента заново не надо, одноразовый код второй раз не нужен.

```sh
# Linux
install -m 0755 /tmp/semaagent ~/.local/bin/semaagent
systemctl --user restart semaagent

# мак
./deploy/install-mac.sh sema.local:8766
```

Живой процесс держит свой файл открытым, поэтому бинарник кладётся рядом и
переименовывается, а не перезаписывается на месте: `install` и `mv` так и
делают, а `cp` поверх работающего файла даёт «text file busy».

Версию агент называет Сёме при знакомстве, и она видна на экране «Агенты»:
обновление не должно быть невидимым. Подставляет её линковщик (`make
build`, `-X main.Version=…`), поэтому собирать надо через `make`, а не
`go build` руками — иначе версия останется «dev».

## Чего на Linux нет

Значка у часов, помощника на Swift и `osascript` на Linux нет, и агент
говорит об этом строкой в журнале при старте, а не падает. Способность
«уведомления» там не объявляется вовсе: показывать нечем, а обещать Сёме
доставку, которой не будет, хуже, чем её не обещать. Всё остальное —
карточки кода, память, хуки — работает одинаково; тегов сборки в коде нет,
бинарник один и тот же под обе системы.

## Шлюз: вход к Сёме из интернета

Шлюз — **другая роль** того же бинарника, и с жителем машины она не
совмещается: житель читает репозитории человека, шлюз стоит лицом к
интернету. Поэтому у него своя служба (`semaagent-gate.service`), своя
учётная запись и своё удостоверение — заводить его надо отдельным
приглашением, выбрав роль «шлюз» там, где Сёма выдаёт код.

**Соединение открывает Сёма**, а не он: у шлюза адрес постоянный,
прячется он. Значит дома не открывается ни один входящий порт, а на машине
шлюза открыт ровно один — тот, куда он звонит. Один на всё: и
управляющий провод, и каждый поток браузера. Один нарочно: Сёму дома
изолируют на роутере, и там разрешается одно направление, а не диапазон.

Два адреса, и путать их нельзя:

| адрес | куда смотрит | пример |
|---|---|---|
| `-gate-sema` | в интернет: сюда звонит Сёма | `0.0.0.0:8767` |
| `-gate-http` | в петлю: отсюда берёт запросы nginx | `127.0.0.1:8770` |

### Порядок

```sh
# 1. бинарник и учётная запись
install -m 0755 /tmp/semaagent /usr/local/bin/semaagent
useradd --system --no-create-home semagate

# 2. служба: подставить @ПОРТ_СЁМЕ@, @ПОРТ_БРАУЗЕРАМ@, @ДОМЕН@
sed -e 's|@ПОРТ_СЁМЕ@|0.0.0.0:8767|' -e 's|@ПОРТ_БРАУЗЕРАМ@|127.0.0.1:8770|' \
    -e 's|@ДОМЕН@|sema.example.org|' \
    deploy/semaagent-gate.service > /etc/systemd/system/semaagent-gate.service

# 3. удостоверение: код выдаёт Сёма на «Агентах», роль там же — «шлюз».
#    Сёма должна быть доступна с этой машины ОДИН раз, только для входа
sudo -u semagate /usr/local/bin/semaagent -enroll <код> -role шлюз \
     -sema http://<адрес Сёмы>:8765 -home /var/lib/semagate

# 4. поднять
systemctl daemon-reload && systemctl enable --now semaagent-gate
journalctl -u semaagent-gate -f
```

Дальше на «Агентах» у Сёмы: разрешить способность «шлюз» тумблером и
вписать публичный адрес шлюза в «Куда звонить шлюзу».

### Что обязан делать nginx

Публичный сертификат держит край, а не шлюз: там, где nginx уже стоит
и умеет certbot, свой ACME отнимал бы у живых сайтов 443. Блок должен
проксировать домен на `-gate-http` и ставить:

- `proxy_http_version 1.1` и подстановку `Upgrade`/`Connection` — без них
  провод живого обновления (`/api/ws`) рвётся на рукопожатии;
- `X-Forwarded-For` — **без него Сёма не узнает настоящего адреса**
  обратившегося, и в её журнале доступа будет один адрес у всех; у Сёмы при
  этом надо включить «Доступ → За своим прокси» (`auth.trust_proxy`);
- `X-Forwarded-Proto` и `Host`;
- `proxy_read_timeout` и `proxy_send_timeout` заметно больше обычных: живой
  сокет молчит между кадрами, и часовой срок здесь не щедрость, а условие
  работы;
- `client_max_body_size` под вложения — общий предел в 128 КБ убил бы
  загрузку файла на краю.

### Где края нет

`-gate-acme` — запасной путь: шлюз сам получает и продлевает
сертификат на домен и сам слушает 443. Нужны свободные 80 и 443, иначе
служба отказывается запускаться, а не воюет за порт молча. Срок своего
сертификата виден Сёме на «Агентах», и о неудаче продления он говорит
заранее, а не в день, когда браузер перестал пускать.

### Выход наружу меняет правила доступа у Сёмы

Снаружи запросы приходят к ней по петле, и отличает их от домашних только
заголовок с настоящим адресом. Поэтому при подключённом шлюзе надо
**выключить** «С этой машины без входа» (`auth.local_open`) и **включить**
«За своим прокси» (`auth.trust_proxy`). Забыли — Сёма скажет об этом на
«Агентах» и уведомлением: молча работать в таком сочетании он не станет.
